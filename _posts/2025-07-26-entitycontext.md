## 2. 영속성 컨텍스트란?

영속성 컨텍스트는 `EntityManager`가 관리하는 **엔티티를 저장하고 관리하는 환경**이다. `EntityManger`를 통해 엔티티를 영속성 컨텍스트에 보관하고 관리할 수 있다. <br />
애플리케이션에서 조회·등록·수정·삭제된 엔티티는 우선 이 컨텍스트에 보관되며, 실제 데이터베이스에는 플러시(flush) 시점에 반영된다. <br />

> EntityManager(엔티티 매니저)
>
> 엔티티(Entity)를 저장하고, 수정하고, 삭제하고, 조회하는 등 엔티티와 관련된 모든 일을 처리하는 관리자의 개념 <br />
> 데이터베이스에 저장하기 전에 먼저 저장되는 일종의 가상 데이터베이스로도 볼 수 있다.

## 3. 엔티티 생명주기

영속성 컨텍스트가 갖는 특징과 장점을 이해하기 위해, 먼저 엔티티의 생명주기를 간단히 알아보자.
![엔티티 생명주기](/assets/img/blog/persistence-context/life-cycle.png)

| 상태           | 설명                                                                |
| -------------- |-------------------------------------------------------------------|
| **Transient**  | `new`로 생성만 된 순수 객체 상태, 아직 영속성 컨텍스트에 등록되지 않음                       |
| **Managed**    | `persist()` 호출 또는 조회(`find()`)로 인해 영속성 컨텍스트에 저장되어  컨텍스트가 관리 중인 상태 |
| **Detached**   | `clear()`, `close()`, `detach()` 등으로 컨텍스트에서 분리된 상태                |
| **Removed**    | `remove()` 호출로 삭제 예약된 상태                                          |

### 비영속 (new/transient)
엔티티 객체를 단순히 생성한 상태

```java
Member member = new Member();
member.setId(1L);
member.setName("아무개");
```
예제 코드에서의 `Member`객체는 새로 생성된 객체일 뿐, 영속성 컨텍스트와는 관련이 없다. 

### 영속(Managed)

엔티티 매니저를 통해 엔티티를 저장하거나, 데이터베이스로부터 조회하여 영속성 컨텍스트에 의해 엔티티가 관리되는 상태   

```java
em.persist(member); // 엔티티를 영속성 컨텍스트에 저장 
em.find(Member.class, id); // 엔티티를 DB에서 조회
```

### 준영속

영속성 컨텍스트가 관리하던 영속 상태의 엔티티를 영속성 컨텍스트가 더이상 관리하지 않는 상태 

```java
em.detach(member); // 엔티티를 영속성 컨텍스트에서 분리
em.clear(); // 영속성 컨텍스트 초기화
em.close(); // 엔티티 매니저 종료
```

### 삭제

영속성 컨텍스트와 데이터베이스로부터 삭제된 상태 

```java
em.remove(member); // 객체를 삭제
```

## 4. 영속성 컨텍스트의 특징 및 핵심 기능

### 특징

1. 엔티티 식별자
- 영속성 컨텍스트는 엔티티를 식별자 값으로 구분한다. 따라서 영속 상태의 식별자는 값이 반드시 있어야 한다.
2. 데이터베이스 저장
- 영속성 컨텍스트에 저장된 값은 보통 트랜잭션(Transaction)이 커밋되는 순간 데이터베이스에 저장된다.
- 데이터베이스에 반영하는 동작을 플러시(flush)라고 한다.

### 1차 캐시 (First-Level Cache)
- 조회 성능을 높이기 위해 영속성 컨텍스트 내부에는 존재하는 캐시 공간을 1차 캐시라고 한다. 
- 영속 상태(Managed)의 엔티티는 모두 1차 캐시에 저장된다. 
- 1차 캐시의 키는 식별자 값으로, 키 값(식별자)을 통해 값(엔티티)를 구분한다. (영속성 컨텍스트 내부에 `Map`이 있다고 생각하면 이해하기가 쉽다) 

영속 상태의 엔티티를 조회하면 다음과 같이 동작한다.
```java
Member member = em.find("member1");
```
![영속 엔티티 조회](/assets/img/blog/persistence-context/persist.png)*영속 상태의 엔티티 조회*

영속 상태의 엔티티가 존재하는 경우, 1차 캐시를 통한 조회가 가능하다. 하지만, 찾고자 하는 엔티티가 영속 상태가 아닌 경우에는 같은 코드에 대해서 다음과 같이 동작한다.
![영속 상태가 아닌 엔티티 조회](/assets/img/blog/persistence-context/not-persist.png)*영속 상태가 아닌 엔티티 조회*

이처럼 영속성 컨텍스트가 제공하는 1차 캐시로 인해, 영속 상태의 엔티티가 존재하면 성능상 이점을 가질 수 있다. 

### 동일성 보장 (Identity Guarantee)

- 영속성 컨텍스트는 “키 기반”으로 엔티티를 관리하므로, 영속성 컨텍스트에 의해 관리되는 엔티티의 키 값이 같은 경우 항상 같은 인스턴스를 반환한다.

코드를 통해 검증해보자.
```java
Member a = em.find("member1");
Member b = em.find("member1");

// true or false ?
System.out.println(a == b);

// result = true
```
같은 키 값에 대해 반복 조회를 실행하게 되면, 1차 캐시 안의 같은 인스턴스를 반환하기에 동일성이 보장된다. 이처럼 영속성 컨텍스트는 1차 캐시의 성능 이점과 인스턴스의 동일성을 보장한다.   

### 쓰기 지연 (Transactional Write-Behind)

- persist()·remove()·변경 감지(Dirty Checking) 로직으로 생성된 SQL을 지연 저장한다.
- 트랜잭션 커밋 또는 em.flush() 시점에 한꺼번에 DB로 전송한다.

```java
EntityManger em = emf.createEntityManager();
EntityTransation tx = em.getTransaction();
tx.begin();

em.pesist(member1);
em.persist(member2);

tx.commit();
```
해당 코드를 실행하면 영속성 컨텍스트는 다음과 같이 동작한다.
![쓰기지연](/assets/img/blog/persistence-context/write-behind.png)*쓰기 지연 동작 과정*

1. 회원 A를 영속화 한다.
2. 영속성 컨텍스트는 1차 캐시에 회원 엔티티를 저장함과 동시에 엔티티 등록 쿼리를 작성한다.
3. 만들어진 쿼리를 쓰기 지연 SQL 저장소에 보관한다.
4. 회원 B에 대해 동일한 절차를 반복한다.
5. 트랜잭션이 커밋 되는 시점에 엔티티 매니저가 영속성 컨텍스트를 먼저 플러시한다.
6. 쓰기 지연 SQL에 저장된 쿼리를 데이터베이스에 보내 영속성 컨텍스트의 변경 사항과 데이터베이스를 동기화 한다.

**JPA에서 쓰기 지연을 지원하는 이유가 무엇일까?**

트랜잭션 안의 코드들은 트랜잭션이 커밋되지 않는 이상, 쿼리를 언제 보내든 데이터베이스에 반영되지 않는다. <br />
그렇기 때문에 JPA는 커밋 직전에만 쿼리를 전달하면 된다. 이것이 바로 트랜잭션을 지원하는 쓰기 지연이 가능한 이유이다. <br /> 또한, 이 기능을 잘 활용하면 모아둔 쿼리를 한 번에 전달할 수 있어 성능을 최적화할 수 있다.

> 쓰기 지연이 지원되지 않는 경우
> 
> GenerationType.IDENTITY 사용 시, 즉시 INSERT 후 키를 받아와야 하므로 해당 엔티티만 예외적으로 쓰기 지연 불가 <br />
> JPQL 벌크 연산(UPDATE, DELETE)은 영속성 컨텍스트를 우회하여 즉시 실행으로 쓰기 지연 불가
{: .prompt-danger }

### 변경 감지 (Dirty Checking)

- JPA에서는 데이터베이스와 달리 직접적인 `update()` 메소드가 존재하지 않는다.
- JPA는 엔티티를 영속화할 때, 최초의 상태를 복사해서 스냅샷으로 저장한다.
- 영속 상태의 엔티티를 수정하면 플러시 시점에 스냅샷의 데이터와 비교하여 변경사항을 데이터베이스에 자동으로 반영해 준다.

영속 상태의 엔티티를 수정하면 다음과 같이 동작한다.
```java
tx.begin();

// 엔티티 조회 (영속 상태)
Member member1 = em.find(Member.class, "member1");

// 영속 엔티티 수정
member1.setName("수정자");

// em.update(member1); 이런 코드는 존재하지 않음
tx.commit();
```
![변경감지](/assets/img/blog/persistence-context/dirty-checking.png)*변경 감지* 

1. 트랜잭션을 커밋하면 엔티티 매니저 내부에서 플러시가 먼저 호출된다.
2. 엔티티와 스냅샷을 비교해서 변경된 엔티티를 찾는다.
3. 변경된 엔티티가 있다면, 수정 쿼리를 생성해서 쓰기 지연 SQL 저장소에 보관한다.
4. 쓰기 지연 저장소의 SQL을 데이터베이스로 보낸다.
5. 데이터베이스 트랜잭션을 커밋한다.

**그렇다면 업데이트 되는 필드는 수정된 부분만일까? 아니면 모든 필드일까?**

JPA의 기본 전략은 모든 필드의 업데이트이다. <br />
모든 필드를 업데이트하면 데이터베이스로 보내는 데이터 전송량이 증가하지만, 다음과 같은 장점들로 인해 모든 필드를 업데이트 한다. <br />

1. 모든 필드를 사용하면 수정 쿼리가 항상 동일하다. 따라서 애플리케이션 로딩 시점에 수정 쿼리를 미리 생성해두고 재사용할 수 있다.
2. 데이터베이스에 동일한 쿼리를 보내면 데이터베이스는 이전에 한 번 파싱된 쿼리를 재사용할 수 있다.

> 동적 UPDATE SQL 
> 
> @DynamicUpdate 어노테이션을 사용하면 원하는 필드만 UPDATE 할 수 있는 전략을 사용할 수 있다. <br />
> 컬럼이 대략 30개 정도가 되면 @DynamicUpdate를 이용한 수정 쿼리가 더 빠르지만, 컬럼이 30개 이상인 경우는 테이블이 적절히 분리되지 않았을 가능성이 높다.
{: .prompt-info }

### 지연 로딩 (Lazy Loading)

- 연관된 엔티티나 컬렉션에 대해 실제 접근할 때 프록시(proxy)를 사용해 DB조회를 지연시키는 방법
- 초기 조회 시 필요한 데이터만 불러와 성능과 메모리를 최적화할 수 있다.

지연 로딩은 프록시 개념과 묶어서 설명하기 위해 따로 글을 작성하겠습니다.

### 정리

| 개념                                     | 설명                                                                 |
|----------------------------------------|--------------------------------------------------------------------|
| **1차 캐시** (First-Level Cache)          | 같은 트랜잭션 내에서 동일 엔티티 조회 시 DB가 아닌 메모리 캐시에서 반환           |
| **동일성 보장** (Identity Guarantee)        | 같은 식별자에 대해 항상 같은 객체 인스턴스를 제공하여 일관성 유지                |
| **쓰기 지연** (Transactional Write-Behind) | `persist`·`remove`·Dirty Checking으로 생성된 SQL을 커밋/flush 시점에 한꺼번에 실행 |
| **변경 감지** (Dirty Checking)             | 관리되는 엔티티의 필드 변경 시 flush 시점에 자동으로 UPDATE SQL을 생성            |
| **지연 로딩** (Lazy Loading)               | 연관 엔티티/컬렉션 접근 시에만 프록시를 통해 SQL을 실행하여 초기 로딩 부담 최소화 |
